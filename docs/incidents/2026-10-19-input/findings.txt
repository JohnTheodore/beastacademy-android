The live workaround is app/src/debug/assets/live-touch-recovery.js. It wraps
only the existing puzzle engine's onMouseEvent method. It filters known phantom
IDs 1 and 2 from the event view passed into that engine. It does not alter
TouchEvent.prototype, dispatch synthetic input, or rewrite raw events seen by
other listeners. New trusted touchstart changes remove reused IDs from the
exclusion set, so a real contact with that ID is accepted. A session-local undo
restores the original engine method and removes the observation listener.

The isolated native test liveRecoveryFiltersOnlyKnownPhantomContactsWithoutReload
passed: establish stale contact 2, verify one-finger drag is blocked, apply the
same JavaScript, verify drag delivery while raw browser contact 2 persists,
verify genuine two-finger movement remains blocked, undo and verify the old
blocked behavior returns, with unchanged performance.timeOrigin.

The workaround was then installed into the original document through read-only
engine discovery followed by one explicit JavaScript method replacement. Before
and after snapshots had the same puzzle trial state and document timeOrigin.
The user confirmed: "Dragging works now". Subsequent inspection showed 90
adapted engine events; the last raw touchend still contained IDs [1,2], while
the engine's adapted touches list was empty. This demonstrates live recovery
without destroying the browser's failure state. It is a targeted current-session
workaround, not a claim that Chromium's contact map has been repaired. It will
not automatically persist after document navigation or app replacement.

Source investigation: Chromium 155.0.8059.84 and Vanadium 155.0.8059.84.0 were
inspected. The browser revision is @5869fe313571d75152b77813cf0a4ee26a4e6df0.
InputRouterImpl::FilterAndSendWebInputEvent retains a nonblocking TouchMove in
last_touch_move_event_ for the SendEmptyGestureScrollUpdate feature. That slot
is flushed by a later touch move or attached to a gesture scroll update. The
nonblocking TouchEnd path does not first flush that slot. An extracted-code
harness demonstrates that MOVE[1,2,3], END1, END2, MOVE[3], END3 is forwarded as
END1, END2, MOVE[1,2,3], END3 and leaves contacts [1,2]. With the feature off,
that harness preserves order and leaves no contacts. Blink's HandleTouchPoint
inserts unknown moved IDs without a hit-tested target, consistent with the
phantom contacts in the real trace having Document targets (no tagName).

This identifies a specific matching source defect. It is not yet a full-browser
reproduction or proof that this exact slot caused the natural incident. Native
replays and desktop-browser replays have so far cleared correctly. Browser
input tracing verifies the empty-scroll-update path is active in the native
lab, but the initial API trace strips event arguments; a later CDP trace retains
them. Further work should target the gesture conditions that leave a move in
that slot across pointer releases, rather than claiming a failed cancellation.
